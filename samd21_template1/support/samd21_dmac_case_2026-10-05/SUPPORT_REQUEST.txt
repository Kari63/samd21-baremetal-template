Subject: ATSAMD21J18A revision D - wrong-channel DMAC writeback despite erratum 1.7.2 workaround

Hello Microchip Technical Support,

Please help investigate an intermittent DMAC channel-context/writeback problem
on an ATSAMD21J18A, silicon revision D, on a SAMD21 Xplained Pro board.
I would appreciate review by an engineer familiar with the SAMD21 DMAC silicon
and erratum 1.7.2, rather than an IDE migration recommendation.

My application is bare-metal C/C++. It runs ADC acquisition and SERCOM5 SPI
display transfers concurrently:

- TC3 MC0 -> asynchronous EVSYS channel 2 -> ADC START.
- ADC RESRDY -> DMA channel 1, LVL3, 16 halfword samples per block, using two
  circularly linked A/B descriptors. ADC was originally assigned channel 6.
- SERCOM5 TX -> channel 4, LVL1, byte beats, source increment enabled.
- SERCOM5 RX -> channel 5, LVL2, byte beats into a fixed dummy sink.
- SPI runs at 12 MHz with RX enabled. Display transfers use up to 2048 bytes
  per single-shot block, DESCADDR=0 and BLOCKACT=INT. RX is armed before TX.
- The next display block is started from the main loop after both DMA
  completion callbacks. Final SPI TXC is awaited before releasing CS.

The source and writeback descriptor tables are separate, 16-byte aligned SRAM
arrays, each holding twelve 16-byte descriptors. CPU interrupt masking protects
the paired SPI descriptor setup and channel register accesses. It does not stop
the DMAC. The application does not intentionally write to the writeback array.

Observed failures:

1. With ADC on ch6 and SPI on ch4/ch5, ch4's source descriptor remained a valid
   SPI TX descriptor, but ch4's writeback contained ADC descriptor fields:
   BTCTRL=0x0909, BTCNT=15, SRCADDR=0x4200401A (ADC RESULT),
   DSTADDR=0x20001100 and DESCADDR=0x200010D0 (ADC's linked descriptor).
   The display stalled. Some earlier stalls showed channel FERR.

2. I moved ADC to ch1 to comply with DS80000760G, section 1.7.2. SPI channels
   4/5 are now higher-numbered than the active linked ADC channel. Nevertheless,
   ADC completion processing eventually stopped while the display and RTC/LCD
   continued. Both ADC source descriptors remained intact, but ch1's writeback
   contained a SPI TX descriptor:
   BTCTRL=0x0409, BTCNT=0x07FF, SRCADDR=0x20000D50,
   DSTADDR=0x42001C28 (SERCOM5 SPI DATA), DESCADDR=0.

The second observation was independently confirmed in the debugger's raw SRAM
view at WRBADDR + 1 * 16 = 0x20001020, not just through a typed Watch expression.
At an ADC-only stall, ch1 was enabled with CHCTRLB=0x00802760,
CHINTENSET=0x03, CHINTFLAG=0 and CHSTATUS=0. ADC INTFLAG was 0x0B.
The ADC completion counter stopped changing and its TERR counter remained zero.
Register readings taken while the CPU is halted may be affected by debug-stop
behavior; the frozen ADC reading was observed while the application was running.

This wrong-writeback symptom occurred with and without per-block SPI channel
SWRST. Failure intervals vary; recent failures appeared after approximately
4-5 hours. One original ch6 run with SPI resets failed after 4 h 32 min.

Erratum 1.7.2 states that enabling a lower-numbered channel while a linked
channel is active can cause FERR or an incorrect descriptor fetch. Its
workaround is to enable channels with numbers higher than the active linked
channels. The ch1/ch4/ch5 configuration follows that numbering condition,
but the wrong-channel writeback observation persists.

Could you please clarify:

1. Is this a broader manifestation of 1.7.2, or another known silicon issue?
2. Are there additional restrictions involving different LVL priorities,
   single-shot channel completion, disable/abort writes, or channel re-enabling?
3. Is continuous linked ADC DMA plus repeatedly started SPI TX/RX DMA supported
   reliably on revision D? What exact register sequence/workaround is required?
4. Could the supplied sequence cause this through software misuse? If so,
   please identify the specific operation and the documented requirement.
5. Is a newer errata document or technical notice available covering this case?

The attachment includes selected original sources, detailed evidence and source
version notes. It is a source review package, not a newly validated standalone
minimal reproducer. The current source snapshot removes redundant SPI disable
writes as a controlled experiment; that change is NOT yet a confirmed fix.
The known-failing pre-change sequence is recorded in EVIDENCE.txt.

A closely matching independent report is:
https://stackoverflow.com/questions/62833342/atmel-samd21-dmac-writeback-failure
It also describes a lower linked channel receiving higher SPI channel data in
its writeback despite following the numbering workaround. This is supporting
context, not proof of the root cause in my application.

Development tools: Atmel Studio 7 / EDBG over SWD, GNU Arm toolchain 6.3.1,
SAMD21_DFP 1.3.395 and CMSIS 5.4.0; Debug build uses -O0 on Windows.

Thank you for reviewing the DMAC behavior and the applicability of the errata.
